# Localisation conventions

How user-facing text is written in SindriCAD so it can be translated. The
runtime is `src/i18n/index.ts`; the catalogue is `locales/en.json`; adding a
language is described in `locales/README.md`.

## The one rule

Every string a user can read goes through `t()`:

```ts
import { t } from "../i18n";
btn.textContent = t("menu.file.save");
toast(t("export.done", { name }));
```

Not through `t()`: unit abbreviations (`mm`, `in`, `°`), file-format names
(`STEP`, `STL`, `3MF`), keyboard shortcut labels (`Ctrl+S`), CSS values, icon
names, log lines, breadcrumbs, anything sent to the sidecar or to Rust, and
error text that is only ever printed to the console.

## Keys

- Nested by area, dot-separated, camelCase segments:
  `menu.file.save`, `sketch.constraint.perpendicular`, `export.error.notWatertight`.
- A key is a stable identifier, **never the English text**. Changing the
  English wording must not change the key, or every translation is invalidated.
- Reuse before adding. `common.*` (OK, Cancel, Close, Esc to close…) and
  `tool.*` (every tool and feature name) already exist; a label that appears in
  the ribbon, the shortcut table and the menu is ONE key used three times.
- Areas in use: `common`, `tool`, `menu`, `ribbon`, `palette`, `sketch`,
  `feature`, `inspector`, `timeline`, `browser`, `params`, `export`, `import`,
  `file`, `print`, `tinkeratlas`, `bug`, `update`, `welcome`, `settings`,
  `shortcut`, `units`, `status`, `gpu`, `engine`, `measure`, `texture`, `text`.

## Parameters

Named, in braces, filled from an object. Never concatenate.

```json
"export.wrote": "Wrote {name} ({count} bodies)"
```
```ts
t("export.wrote", { name, count: bodies.length })
```

Parameters are data: a body name, a number, a file name. They are never
translated and never contain markup. If the result goes into `innerHTML`, wrap
the WHOLE call in `esc()` and pass the raw (unescaped) parameter:
`esc(t("x", { name }))`. Locale strings themselves never contain HTML; when a
sentence needs markup in the middle, split it into two keys.

## Plurals

An entry may be an object keyed by CLDR category; `other` is required, the
rest optional. `t()` selects with `Intl.PluralRules` for the active locale from
the `count` parameter.

```json
"browser.deleted": { "one": "Deleted {count} body", "other": "Deleted {count} bodies" }
```

No `n === 1 ? "body" : "bodies"` at a call site, no spliced stems
(`bod${…}`), no English articles glued onto a translated noun. If the grammar
of a sentence depends on something other than a count, make it two keys.

## Lists

`a, b and c` is English grammar. Use `new Intl.ListFormat(localeTag()).format(items)`
from `src/i18n` when joining a list for display.

## Where the key of an element must be discoverable

Prefer `setText(el, key, params)` and `setTitle(el, key)` over assigning
`textContent`/`title` from `t()`. They also stamp `data-i18n`, which is how the
bug reporter's "translation issue" category knows which string the user was
looking at. Inside `innerHTML` templates, add `data-i18n="the.key"` on the
element by hand when it is cheap.

## Messages that cross a process boundary

The sidecar and the Rust shell send a stable `code` next to their English
`message`. The UI maps a code it knows to `t("engine.error.<code>")` and shows
the English message for one it does not. Rust and Python never carry
translations, and log lines, crash reports and the bug-report payload stay
English so support can search them.

## Checking

- `npm run i18n:check`: keys missing from a locale (warn), keys in a locale
  but not in English (fail), entries identical to English (warn).
- `npm run i18n:lint`: string literals that look like UI text outside `t()`.
- Run the app with the pseudo-locale (Settings → Language → Pseudo-locale):
  any text WITHOUT brackets skipped `t()`; any clipped text is a layout to fix.
